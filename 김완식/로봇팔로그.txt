로그에서 핵심 두 가지가 보입니다.
1. 로봇팔 USB는 "USB-C 연결"로 인식되긴 했습니다
이 줄들이 중요합니다:
l4tbr0: port 1(usb0) entered forwarding state
IPv6: ADDRCONF(NETDEV_CHANGE): l4tbr0: link becomes ready
fusb301 ... fusb301_detach
tegra-xudc 3550000.usb: ep 3 disabled

fusb301은 오린의 USB-C 포트 컨트롤러입니다. detach / ep 3 disabled는 USB-C에 뭔가 꽂혔다 빠지는 걸 감지한 로그입니다. 즉 ws님이 케이블 재연결할 때 이게 반응한 겁니다.
l4tbr0 + usb0는 USB 네트워크(USB gadget) 인터페이스입니다. 오린이 USB-C로 연결된 상대를 시리얼이 아니라 네트워크 장치로 잡았다는 뜻입니다.

이게 결정적입니다. 로봇팔이 /dev/ttyUSB(시리얼)로 안 잡힌 이유 — myCobot 280 Pi는 자체 라즈베리파이가 있어서, USB-C 직결 시 시리얼 포트가 아니라 USB 네트워크로 동작합니다. 예상대로 USB-serial 직결 방식이 아닙니다.
즉 로봇팔 제어는 네트워크(IP)로 해야 합니다. 메모리에도 로봇팔이 .102 IP를 가진 걸로 돼 있었죠. USB-C로 연결하면 그 사이에 USB 네트워크가 생기는 구조일 수 있습니다.
2. NVIDIA modeset 에러 — 무시해도 됨
nvidia-modeset: ERROR: GPU:0: Failed to allocate ... DRAM
failed to set bandwidth for 7: -134
이건 디스플레이(HDMI/DP) 출력 관련 에러입니다. ws님은 헤드리스(VNC)로 쓰니까 모니터가 안 붙어있어서 나는 경고입니다. GPU 연산(YOLO)이나 로봇 동작과는 무관하고, 실제 동작에 영향 없습니다. 헤드리스 젯슨에서 흔히 나오는 로그입니다.
3. EXT4-fs 에러 — 살짝 신경 쓸 것
EXT4-fs (mmcblk0p1): last error at time 786: __ext4_new_inode
SD카드/스토리지 파일시스템에 과거 에러 기록이 있다는 뜻입니다. 지금 당장 문제는 아니지만, ws님 메모리에 AGV SD카드 손상 복구 이력이 있었던 걸 보면 스토리지 안정성은 주기적으로 봐두는 게 좋습니다. 지금 급한 건 아닙니다.
정리 + 다음 단계
로봇팔은 USB-serial이 아니라 **USB 네트워크 또는 별도 IP(.102)**로 연결됩니다. 연결 확인하려면 시리얼이 아니라 네트워크로 봐야 합니다.
USB-C로 생긴 네트워크 확인:
baship addr show usb0
ip addr show l4tbr0
또는 로봇팔 IP로 핑(메모리상 .102):
bashping -c 3 192.168.0.102
먼저 알려주세요 — 로봇팔을 USB로 직접 제어하려는 건가요, 아니면 네트워크(.102)로 ROS2 통신하려는 건가요? myCobot 280 Pi는 후자가 정석이라, 목적에 따라 확인 방법이 갈립니다. 위 ip addr / ping 결과도 같이 주시면 연결 상태를 정확히 짚어드리겠습니다.
